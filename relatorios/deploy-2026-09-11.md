## 3. O runbook

### Fase 0 — antes de tocar em qualquer coisa

```bash
export PATH="$HOME/.local/bin:$PATH"
cd /home/arleson/Documentos/a-dois
git status --short && git log --oneline -1     # árvore limpa, 6c39538
npm run typecheck && npm run lint && npm test && npm run test:rls && npm run guardas
```

### Fase 1 — Supabase (você, no painel)

1. Criar projeto. **Região: São Paulo (`sa-east-1`)**. Guardar a senha do banco: ela não
   aparece de novo.
2. Database → Extensions → habilitar **`pg_cron`**. Sem isso o push morre na 4ª migration.
3. Auth → URL Configuration: **deixe para depois da Fase 3** se você não tem domínio
   próprio. Ela não bloqueia o deploy — só o link do e-mail de confirmação fica errado
   até você preencher. Sem domínio, o valor certo é a URL `.vercel.app` que a Vercel
   atribui no primeiro deploy (dá para escolher o nome em Project Settings → General →
   Project Name, o que fixa a URL como `https://<nome>.vercel.app`). Depois do deploy,
   volte aqui com essa URL:
   - **Site URL**: `https://<nome>.vercel.app`
   - **Redirect URLs**: `https://<nome>.vercel.app/auth/confirm`

   Deploys de preview (toda branch que não é a de produção) ganham URL própria da
   Vercel e não vão ter confirmação de e-mail funcionando, a menos que você cadastre
   cada uma ou use um wildcard **escopado ao seu projeto**
   (`https://<nome>-*.vercel.app/auth/confirm`) — evite `*.vercel.app` sozinho, que
   entraria na allowlist para qualquer projeto de qualquer pessoa na Vercel, não só o
   seu. Para o teste de fumaça, produção basta.
4. Auth → SMTP Settings: um remetente próprio (Resend, SES, Postmark — qualquer um). E no
   domínio: **SPF, DKIM e DMARC**, senão o Gmail manda para spam.
5. Auth → Email Templates: colar `supabase/templates/confirmacao.html` e
   `recuperacao.html`. O `content_path` do `config.toml` **só vale no local**.
   Os dois apontam para `/auth/confirm?token_hash=...`, e é isso que faz o cookie
   `httpOnly` funcionar — o fluxo padrão da Supabase devolve o token no fragmento da URL,
   que só JavaScript lê.
6. Auth → Rate Limits: conferir o limite de envio de e-mail. O `email_sent = 30` do
   `config.toml` é do ambiente local e não sobe junto.

### Fase 2 — o schema

```bash
supabase login
supabase link --project-ref <ref-do-projeto>
supabase db push --dry-run     # lê as 11 e não aplica nada
supabase db push
```

> **Não rode `supabase config push`.** Ele aplicaria o `config.toml` local — inclusive
> `site_url = "http://localhost:3000"` — por cima do que você acabou de configurar.

Conferir que as 11 entraram e que o job do expurgo existe:

```bash
supabase db execute "select count(*) from supabase_migrations.schema_migrations"
supabase db execute "select jobname, schedule from cron.job"
```

### Fase 3 — Vercel

1. Importar `arlesonbaracho/a_dois`.
2. **Root Directory**: `apps/web` · **Include files outside root directory**: ligado.
3. Framework: Next.js. Build e install ficam no padrão — o `transpilePackages` do
   `next.config.ts` já resolve os pacotes do workspace.
4. Environment Variables (Production **e** Preview):
   - `NEXT_PUBLIC_SUPABASE_URL` = `https://<ref>.supabase.co`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` = a anon key
   **Só essas duas.** Se a service role key aparecer aqui, pare tudo: ela vai para o
   bundle do cliente e a regra 4 do CLAUDE.md caiu.
5. Deploy. Depois, apontar o domínio e **voltar ao passo 1.3** para trocar o Site URL se
   o domínio final for diferente do `.vercel.app`.
